## Design points, and why

* **Sign-in happens in the WebSocket handshake.** The page opens `/ws` with
  two subprotocols: `activity-session`, then its session token. The server
  checks the token in the upgrade handler and answers 401 before a socket
  exists, so a caller without a valid session holds no slot, no timer and no
  connection. The server's answer names `activity-session` only, so the token
  is never echoed, and no message ever carries it. A query parameter would
  also work but would put the token in access logs, so it is not built.
* **The sign-in limit is per code plus one shared bucket.** Discord documents
  no header with the player's address, and says the proxy exists to hide it.
  The address that reaches the app is the proxy's, shared by every player, so
  a per-address limit would act as one global limit anyway. The per-code
  limit (3 tries in 10 minutes) stops one code being replayed. The shared
  token bucket (a burst of 120, refilled at 2 a second) stops anyone making
  the app hammer Discord's token endpoint with made-up codes, and recovers
  smoothly instead of at the top of each minute. Malformed requests and
  requests that are not JSON are refused before they count. When Discord
  answers 429, sign-ins answer 503 for as long as its `Retry-After` says,
  without calling Discord. The cost: a flood of well-formed fake codes can
  delay real sign-ins while the bucket is empty. It cannot get the app's
  Discord credentials rate limited, and no `X-Forwarded-*` header is read.
* **The session key is per application.** It is HKDF-SHA256 of the client
  secret, with a fixed label and the client ID as the info string. A token
  from one Discord application is refused by another, even with the same
  secret. Signatures must be in their one canonical base64url spelling.
* **The ping is an application message.** The proxy runs on Cloudflare
  Workers, and Discord does not say whether WebSocket ping frames pass end to
  end. A `{"t":"ping"}` text message every 25 seconds, answered by the page,
  crosses any relay and also tells the server the page is alive. A socket
  silent for 60 seconds is closed.
* **The instance ID travels in the session token.** The page sends it with
  the code to `/api/token`, and the server signs it into the session token
  next to the user ID. The ID itself comes from the player's Discord client
  and is checked only for shape. The README says so, and points to Discord's
  activity instance endpoint for a game with stakes.
* **The session is checked at the handshake only.** An open socket keeps
  working after its token expires. The page renews before any reconnect that
  would present an expired token, and signs in again after any socket that
  closes before "welcome" (the browser reports a refused handshake as 1006).
  A copy that adds kick or ban needs revocation on the server; the README
  says so.
* **Every refusal is bounded in time.** A refused or misbehaving socket gets
  a close frame, and is cut one second later if it has not answered.
* **Close codes.** 401 at the handshake (sign in again), 4003 (too many
  connections, room full, server full: retry in 15 seconds), 1001 (server
  restarting: reconnect), 1008, 1009, 1003 and 1007 (bounds and bad
  messages).
* **Abuse bounds in the code, not platform limits.** 1,000 open sockets,
  200 rooms, 50 sockets a room, 6 sockets a player across rooms, 3 in one
  room, 1 MB of unsent data per socket. All in `server/src/limits.js`. At the
  room cap, the room that has been empty longest makes way; "server full"
  only when every room has someone in it.
* **A refused handshake is released at once.** The server writes the 401 or
  503 answer and destroys the connection as soon as it is written, so a peer
  that keeps its side open holds nothing. (After the upgrade event the
  connection belongs to the app alone: no HTTP timeout applies to it.)
* **The game page's Content-Security-Policy** is `default-src 'self';
  connect-src 'self'; base-uri 'none'; form-action 'none'`, with no
  `frame-ancestors`, because Discord shows the page in its own frame.
  `/api/config` returns the client ID only. The setup page, shown only while
  the app is unconfigured, still names the URL mapping target.

by Trails, a realtime light-cycle arena. What changed: `server/src/game.js`,
its wiring in `server/src/server.js` (the game clock, the full state sent on
join, the `ride`, `watch` and `turn` handlers, and a presence update when a
socket joins or leaves), the page's game view (`client/src/trails.ts`,
`client/src/style.css`), the game's tests, `tests/load.mjs`,
`tests/probe.mjs` and the new `tests/bench.mjs`.

### Rules and design

| | |
| --- | --- |
| Board | 64 x 64 cells. Each room keeps one `Uint8Array` of 4,096 bytes: 0 for empty, else the rider's place plus one. |
| Clock | 15 ticks a second, on the server. Every rider still in moves one cell a tick. |
| Riders | At most 8 a room; everyone else watches. A colour per rider, the first one free. |
| Crashes | A wall, any trail (the rider's own too), heads entering one cell (all out), two heads swapping cells (both out: a head is part of its trail). Every move is checked against the board as it was before the tick, so the order of riders does not matter. Trails stay until the round ends. |
| Turns | Two may wait between ticks; more are dropped. One applies per tick, so a quick double turn works over two ticks. A reversal, the current direction, an unknown direction, and a turn from someone with no cycle in the round are ignored, without an answer. A turn only ever steers the sender's own cycle: the server takes the player from the session, never from the message. |
| Round | Lobby; a countdown of 3 s once at least one rider is in the room; play; 3 s of results; then the next countdown by itself while riders remain. A round that started with two or more ends when one (or none) is left; a round ridden alone is practice and ends when its rider crashes. Riders who join during play wait for the next round. A countdown that gains or loses a rider respawns everyone, at most once a tick, and is lengthened to a second once at most, so riders coming and going cannot hold it open. |
| Spawns | Evenly spaced on a ring of radius 20 around the centre, turned one place each round, each facing clockwise along the ring. A spot on a trail, next to another spawn, or one cell from a wall, a trail or another rider's first move slides along its radius until it fits. |
| Leaving | A rider whose sockets have all closed keeps riding straight on until they crash; the same user on a new socket steers again. After 30 s away the place is freed. Choosing Watch during play takes the rider out of that round. |
| Scoreboard | Wins per user, in the room's memory, gone with the room or a restart. The top 10 are shown; 64 users are kept. Practice counts no win. |
| Game clock | One timer for every room with riders (or something left to send), drift corrected, stopped when no room needs it: an idle server runs no game timer. One shared timer rather than one per room, because 200 busy rooms then cost one wake-up a tick instead of 200, all rooms tick in step, and a room the server evicts or sweeps cannot leave a timer behind (the clock skips it and lets go). The timer stays marked as running while rooms step, so a socket closing in the middle of a tick cannot start a second one, and shutdown stops it. |
| A failing room | A room whose step throws is closed on its own: one log line ("A room failed with an internal error and was closed.", at most once a minute), its sockets closed with 1011, the room dropped. Every other room ticks on, and the same Activity instance gets a fresh room on reconnect. |

Messages from the page: `{"t":"ride"}`, `{"t":"watch"}`,
`{"t":"turn","d":"up"}` (or `down`, `left`, `right`) and the existing
`{"t":"pong"}`. A turn goes out only on a key press, a swipe or a button, at
most 12 a second (the page's own limit, under the server's 20 messages a
second), and never once a frame.

Messages from the server, besides `welcome`, `ping` and `error`:

| Message | When | Shape |
| --- | --- | --- |
| `state` | on join, and when a round is set up or ends in the lobby | `size`, `hz`, `phase`, `ms` left in the phase, `n` (ticks played), `cycles` (`id`, `name`, `c` colour, `alive`, `dir`, `pts`: the trail as its corners, the last one the head), `result`, `riders` (`id`, `name`, `c`, `here`), `people` (`id`, `name`), `scores` (`id`, `name`, `wins`) |
| `tick` | every tick of play | `n`, `h` (each rider's new head cell, `y * 64 + x`, or -1), and `out` (places in the list) only when someone went out. Largest seen: 74 bytes with 8 riders. |
| `phase` | play starts; the round is over | `phase`, `ms`, and on `results` a `result`: the winner (or none), or for practice the rider and the time survived |
| `roster` | riders, people or scores changed, at most once a tick, and only when different from the last one sent | `riders`, `people`, `scores` |

The page draws the board on a canvas, about 1.2 ticks behind the newest tick
on a clock kept in step with the server's, so heads glide between ticks and a
late tick causes a pause rather than a jump. A turn the player just asked for
shows at once as an arrow on their own head.

The eight colours were picked by measurement: the smallest CIEDE2000
difference between any two of them is 19.6 for normal colour vision, 9.8
under simulated protanopia, 11.5 under deuteranopia and 7.3 under tritanopia
(Machado et al. 2009, full severity), and their brightness runs from dim blue
to white as a second cue. The names next to the heads are the third. A first
pick with gold in place of orange scored well on paper but drew gold and
yellow alike on the board, so orange replaced it.

### Tested

* **Rules, without sockets** (`server/test/game.test.js`, 26 cases): each
  wall; the rider's own trail; another rider's trail, which stays for the
  round; two heads into one cell; three heads into one cell (all three out,
  the cell left empty, the fourth rider wins); two heads swapping cells; the order of
  riders not mattering; a reversal, the current direction and 11 unknown
  directions ignored (including `__proto__`, `constructor`, a number, null and
  an array); two buffered turns making a quick double turn while a third is
  dropped; 100 turns a tick for 40 ticks never moving a cycle more than one
  cell or straight back; a turn from a player without a cycle, and from one
  rider for another, changing nothing; spawns for 1 to 8 riders over every
  rotation, on the ring, evenly spaced, clockwise, never adjacent, with all
  spawns and first moves on different cells; spawns moving off a trail laid
  over the ring, and none when no spot fits; the whole round flow; a round of
  three to a winner and the scoreboard over three rounds; practice; a mid-round
  rider waiting; a countdown respawning with a second left; a countdown
  still reaching play within 4 s while a rider toggles Ride and Watch every
  10 ticks (before the fix it never did); a closed socket's
  cycle riding on and the same player steering again; the place freed after
  exactly 30 s and kept for a rider back in time; Watch during play; 8 riders
  at most, each with their own colour; a tick with 8 riders well under 1 KB;
  the board rebuilt from the messages, from the start of a round and from a
  snapshot mid-round, equal to the server's board; the roster sent only when
  it changes.
* **Over real sockets** (`server/test/ws.test.js`): two signed-in riders and
  a spectator; the spectator's turns (naming the riders in the message) get
  no answer and change nothing; one rider turns, the other rides straight;
  a round to a winner; every tick in order and under 1 KB; the scoreboard;
  the next countdown by itself. A flood of 100 turns from a rider: its
  direction changed twice (every run so far; the test allows 4, for a burst
  that straddles a tick), the socket closed with 1008 at the existing limit,
  its cycle rode on, the other rider kept getting ticks and `/health`
  answered. A rider whose socket closed: its cycle rode straight on, the
  roster showed it away, and the same user on a new socket got the whole
  board and steered again. A room made to throw on its next step: its
  socket closed with 1011 "room error", the room was gone, one log line,
  a rider in another room went on from the countdown to play and ticks,
  `/health` answered, and the same Activity instance got a fresh room.
* **Existing security tests:** all still pass. Three that used the old
  game's messages (identity from the token, the 4 KB limit, the 20-a-second
  limit) now use `ride` to show a socket still works; what they assert is
  unchanged.
* **Smoke test and browser check:** above.

### Load and resources

Measured with `docker stats` and the container's own CPU counter
(`cpu.stat`), under the smoke test's limits (`--cpus 0.25`, 256 MB, uid 1001,
read-only), on the current image. The load is `tests/load.mjs`: 20 signed-in
sockets in 3 rooms (7, 7 and 6 riders), every rider riding every round,
turning at random now and then and steering away from a wall or trail just
ahead, for 10 minutes, through the internal network. Each rider rebuilt the
board from the server's messages and checked every tick against it.

| | Memory | CPU (share of one core) |
| --- | --- | --- |
| Idle, 30 to 60 s after start, 6 samples | 14.2 MiB | 0% |
| 10 minutes of play, 46 samples every 10 s | 16.6 to 20.7 MiB, peak 20.7 MiB (8% of 256 MB) | 1.69% on average over the run (10.2 s of CPU in 602 s), highest 10-second sample 9.3% (the others 0.6% to 5.6%) |
| 20 s after the load ended | 20.0 MiB | 0.2% (the rooms still hold their riders' places for 30 s) |

The run played 95 rounds, each with a winner, 18,309 ticks across the three
rooms, and sent 11,152 turns. Every rider's board matched every tick (0
mismatches), no socket closed, no error came back, the largest tick was 69
bytes, and the app did not restart and was not killed for memory. Its log
held only its two start lines. During play the rooms got a steady 15 ticks a
second (15.00 on average over the 95 rounds, the slowest round 14.96), and no
two ticks arrived more than 119 ms apart.

More riders, 2 minutes each, the same limits unless noted. "Ticks a second"
is what each room's first rider received during play, averaged over the
rounds, with the slowest round after it.

| Riders (rooms of 8) | CPU, average | Ticks a second | Longest gap | Memory, peak |
| --- | --- | --- | --- | --- |
| 200 (25) | 8.1% | not measured (before the load counted it) | | 28.0 MiB |
| 400 (50) | 13.5% | 14.6, slowest 11.5 | 311 ms | |
| 504 (63) | 16.3% | 14.5, slowest 10.3 | 390 ms | |
| 600 (75) | 19.4% | 14.3, slowest 8.8 | 481 ms | |
| 400 (50), CPU limit 4 instead of 0.25 | 14.6% | 15.0, slowest 15.0 | 88 ms | |

Every one of these runs: 0 mismatches, no socket closed, no error. The load
client stayed near a third of one core, so it was not the bottleneck. CPU
grows with the number of riding sockets (about 0.03 to 0.04% of one core
each), because every tick is one small write per socket; the game's own work
is a small part of it, as the benchmark shows. With many riders the average
stays under the limit, but a busy tick can use up the CPU limit's share for
the moment and wait for the next one: the rate dips and gaps open. Without
the limit the same 400 riders got a steady 15. The socket cap (1,000) bounds
memory, not CPU.

### Benchmark: 200 rooms of 8 riders, in one process

`node tests/bench.mjs 200 8 <seconds> [realtime]`: 200 rooms, 1,600 riders,
every room stepped each tick and every message serialised once, as the
server's broadcast does. Only that work is timed (not the riders' choices,
not the sockets).

| Where | Mode | Per tick, all 200 rooms | Share of one core at 15 a second | Kept | Heap after |
| --- | --- | --- | --- | --- | --- |
| Development machine, Node 22.22.1 | as fast as it runs, 120 game seconds | mean 0.68 ms, median 0.57 ms, p99 2.35 ms | 1.0% | 1,272 rounds | 9.5 MB |
| The image, `--cpus 0.25`, 256 MB | on a 15-a-second timer, 60 s | mean 1.81 ms, median 0.94 ms, p99 31 ms | 2.7% | 14.96 ticks a second; the whole process (riders included) used 3.8% of one core | 9.4 MB |

The p99 under the CPU limit is the container being held back by its CPU
share in bursts, not the game: the median stayed under a millisecond and the
clock kept its rate. 200 rooms of 8 send about 2,000 messages a second before
fan-out, 770 bytes a second per room.
